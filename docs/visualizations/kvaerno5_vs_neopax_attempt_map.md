# Kvaerno5 rejection handling versus NEOPAX's historical attempt replay

Source audit and scalar CPU comparison, 2026-10-30. No plasma, VMEC or NTX
calculation was run. The numerical results are saved in
[kvaerno5_rejected_steps.json](kvaerno5_rejected_steps.json), generated by
[`check_diffrax_kvaerno5_rejected_steps.py`](../../examples/benchmarks/check_diffrax_kvaerno5_rejected_steps.py).

## Confirmed historical NEOPAX difference

Commit `0fed61d33c15262f80881cdc4b09fd675dc85a98` (`Recovering ad reverse`,
2026-06-23) changed `_radau_replay_realized_attempt_rollout`.

Before that commit, the rejected branch preserved physical `y` but recomputed an
attempt and replaced the following carry fields with stopped-gradient outputs:

- `lagged_response_cache` and `lagged_reference_y`;
- Jacobian/LU reuse data and associated validity/age fields;
- other numerical/controller metadata.

The commit replaced this with `next_carry = carry`: the derivative replay's
complete carry remains unchanged on a rejected slot. This describes the
derivative replay, not a rule forbidding the original adaptive solver from
performing rejected trials or maintaining numerical caches.

This is a concrete difference from simply discarding an unused trial state.
`stop_gradient(new_cache)` changes the cache value used later and removes the
derivative of that replacement. It does not restore `old_cache` and its existing
parameter dependence. A lagged transport response/reference is particularly
relevant because it participates in later RHS evaluations. Ordinary Newton
Jacobians/LU factors are a separate issue: accurate converged implicit-stage
derivatives should not require differentiating the nonlinear solver's numerical
factorization history.

This audit confirms the implementation change. It does **not** identify which
field produced the user's remembered large gradients, recover their numerical
values, or demonstrate that this was their entire cause. The memory-free cooling
animation cannot establish gradient equality for that earlier NEOPAX map.

## Diffrax Kvaerno5 source comparison

Inspected installed Diffrax 0.7.2 and the corresponding current upstream code:

| Behavior | Historical NEOPAX derivative replay, before `0fed61d` | Diffrax Kvaerno5 + PID + default checkpointed adjoint |
| --- | --- | --- |
| Physical state on rejection | Keep old `y` | Keep old `y` |
| Persistent auxiliary solver data on rejection | Replace selected cached values with stopped-gradient attempt outputs | Select the old solver state |
| Timestep/controller differentiation | Realized metadata is frozen | PID stops gradients through the error-based adaptation factor |
| Implicit nonlinear stage solves | NEOPAX's custom stage derivative machinery | Optimistix implicit adjoint for the converged root |

Kvaerno5 is an ESDIRK 5/4 method with seven stages and an FSAL endpoint-RHS cache.
Its returned persistent solver state is `(first_step, f0)`. Rejection rolls that
state back with the physical state. Its default VeryChord linearization is
prepared per attempted step and shared across stages; it is not a persistent
rejected-step transport-response cache. Implicit root differentiation uses the
stage equation rather than differentiating the chord iteration history.

Primary sources:

- [Kvaerno5 method documentation](https://docs.kidger.site/diffrax/api/solvers/ode_solvers/#diffrax.Kvaerno5).
- [Integrator state selection](https://github.com/patrick-kidger/diffrax/blob/main/diffrax/_integrate.py).
- [Runge--Kutta stage solves and returned solver state](https://github.com/patrick-kidger/diffrax/blob/main/diffrax/_solver/runge_kutta.py).
- [VeryChord initialization](https://github.com/patrick-kidger/diffrax/blob/main/diffrax/_root_finder/_verychord.py).
- [PID stop-gradient](https://github.com/patrick-kidger/diffrax/blob/main/diffrax/_step_size_controller/pid.py).
- [Optimistix implicit-adjoint contract](https://docs.kidger.site/optimistix/api/adjoints/).

## Scalar check using real Kvaerno5

Problem: `T'=-k*(T-20)`, `T(0)=80`, `k=0.2 min^-1`, final time 10 minutes.
The solver evolves excess temperature `y=T-20`. The initial proposed timestep is
8 minutes, PID tolerances are `rtol=1e-6, atol=1e-9`, and the solve is capped at
128 attempts. VeryChord uses explicit `rtol=1e-10, atol=1e-12` in **both** runs,
so switching to `StepTo` does not change the nonlinear tolerances.

The baseline uses Diffrax's normal adaptive attempt loop and
`RecursiveCheckpointAdjoint`. The second solve uses `StepTo` on the baseline's
recorded accepted times, preserving Kvaerno5/FSAL propagation on accepted steps.
The FD perturbs k on the same accepted schedule; it does not rerun the controller.

| Quantity | Result |
| --- | ---: |
| Accepted / rejected steps in adaptive baseline | 7 / 2 |
| Adaptive / replay final temperature | 28.120135238437182 deg C / same |
| Adaptive attempt-loop AD | -81.20081790406365 |
| Accepted-time replay AD | -81.20081790406365 |
| Frozen-schedule FD, step 1e-6 | -81.20081790519151 |
| Continuous exact derivative | -81.20116994196762 |
| Absolute adaptive/replay gradient difference | 0 |

The discrete gradient need not equal the continuous exact derivative at finite
solver tolerance. This case shows that rejected attempts do not inherently create
large gradients in Kvaerno5. It does not reproduce NEOPAX's lagged-response cache
or prove the cause of a historical transport discrepancy.

Environment: CPU, JAX 0.11.2, Diffrax 0.7.2, Optimistix 0.1.0, Equinox 0.13.8,
Lineax 0.1.1. Reproduce this bounded scalar check with:

```bash
JAX_PLATFORMS=cpu python examples/benchmarks/check_diffrax_kvaerno5_rejected_steps.py
```
